# HMS.Api — Backend for BIC SmartCare

ASP.NET Core 8 Web API + Entity Framework Core + SQL Server. Mirrors every mutator that
used to live in the frontend's `DataContext.jsx` (add patient, adjust payment, apply →
verify → approve/reject → pay EMI, appointment status changes) as real, authenticated,
database-backed endpoints.

## First-time setup (SQLite — zero database setup required)

This project is configured to use **SQLite** by default: a single local file (`hms.db`),
no SQL Server install, no service to start. This is ideal for quickly checking the
project runs end-to-end. (If your SEP submission specifically requires SQL Server, see
the "Switching to SQL Server" section at the bottom — it's a 3-line change.)

```bash
cd HMS.Api
dotnet restore

# Install the EF Core CLI tool once, globally, if you don't have it:
dotnet tool install --global dotnet-ef

dotnet ef migrations add InitialCreate
dotnet run
```

That's it — no connection string to edit. On first run, `hms.db` is created automatically
in the `HMS.Api` folder and seeded with the same demo data (doctors, patients, bills,
EMI plan) as before.

**IMPORTANT before your demo/showcase:** also change `Jwt:Key` in `appsettings.json` to
your own long random string — never ship the placeholder value.

The API listens on `https://localhost:7xxx` (check the console output for the exact
port) and exposes Swagger UI at `/swagger` in development.

## Switching to SQL Server later

If you need SQL Server specifically (e.g. it's a stated requirement), it's a 3-step swap:
1. In `HMS.Api.csproj`, replace the `Microsoft.EntityFrameworkCore.Sqlite` package
   reference with `Microsoft.EntityFrameworkCore.SqlServer` (same version number).
2. In `Program.cs`, change `opts.UseSqlite(...)` to `opts.UseSqlServer(...)`.
3. In `appsettings.json`, change the `Default` connection string to your SQL Server
   instance, e.g. `Server=(localdb)\\mssqllocaldb;Database=HmsDb;Trusted_Connection=True;`
   for LocalDB, or `Server=localhost\\SQLEXPRESS;Database=HmsDb;Trusted_Connection=True;TrustServerCertificate=True;`
   for SQL Server Express.
4. Delete the `Migrations` folder and run `dotnet ef migrations add InitialCreate` again
   (migrations are provider-specific, so they need regenerating after switching).

## Endpoint map

| Area | Endpoints |
|---|---|
| Auth | `POST /api/auth/login/admin`, `/login/doctor`, `/login/patient`; `GET /doctor-options`, `/patient-options` |
| Doctors | `GET /api/doctors`, `GET /api/doctors/{id}`, `POST /api/doctors` (admin) |
| Patients | `GET /api/patients` (role-scoped), `GET /api/patients/{id}`, `POST /api/patients` (admin) |
| Departments | `GET /api/departments` |
| Appointments | `GET /api/appointments` (role-scoped), `POST`, `PATCH /{id}/status` |
| Billing | `GET /api/bills` (role-scoped), `POST` (admin), `POST /{id}/adjust-payment` (admin) |
| EMI | `GET /api/emi/applications`, `GET /api/emi/plans`, `POST /api/emi/apply` (patient), `POST /api/emi/applications/{id}/verify` (admin), `/approve`, `/reject`, `POST /api/emi/plans/{billId}/pay-installment` |
| Reports | `GET /api/reports` (role-scoped), `POST` (doctor/admin) |
| Dashboard | `GET /api/dashboard/stats`, `/revenue-trend`, `/department-load` (admin) |

Every endpoint except the two login-option lists requires `Authorization: Bearer <token>`.
Role scoping is enforced **server-side** (a doctor's JWT can only ever pull their own
patients — not because the frontend hides the button, but because the API itself checks
the `refId` claim). That server-side enforcement is exactly the kind of thing SEP judges
ask about when they poke at "what if I just call the API directly."

## Why ID formats look the way they do

IDs like `PT-1043`, `AP-3306`, `BL-5502` are generated by `IdGenerator` reading from an
`IdCounters` table — this exactly mirrors the `nextId()` counter that used to live in
`DataContext.jsx`, so nothing in the frontend's rendering logic needs to change.

## Known trade-offs (mention these if asked — they show you understand the system, not just copied code)

- Passwords are hashed with BCrypt, but the assignment's demo passwords (`admin123`,
  `doctor123`, `patient123`) are still simple stand-ins — that's a deliberate demo
  choice, not a production one.
- JWTs are unencrypted bearer tokens with no refresh-token rotation — fine for a
  showcase, would need refresh tokens + shorter expiry for production.
- `EmiPlan` denormalizes `Patient` name onto the plan/bill rows (matching the original
  mock data) rather than always joining — a deliberate read-speed trade-off worth
  naming if a judge asks about normalization.
